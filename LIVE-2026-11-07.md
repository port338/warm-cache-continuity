# Live delivery check — 2026-11-07

The clean-install report covers the gate logic in isolation. This note covers the two things a
sandbox cannot prove: that the **scheduler really stays silent when the gate says no**, and that a
**fired ping really reaches a chat**.

Environment: production OpenClaw 2026.10.7, Linux 6.8, Node 24.22.1, one Telegram account
connected, the watcher scheduled `*/20 * * * *` in `Europe/Moscow` with
`sessionTarget: isolated` and `delivery.mode: announce`.

All numbers below are read back from the automation record (`triggerEvalCount`,
`lastTriggerFireAt`, run history) and from the delivery trace of each run — not from logs written
by the agent.

## 1. A fired ping reaches the chat

| Field | Value |
|---|---|
| Scheduled slot | 10:00 MSK (weekend window opens at 10:00) |
| `triggerFired` | `true` |
| Agent usage | 10 554 in / 658 out tokens |
| `delivered` | `true` |
| `deliveryStatus` | `delivered` |
| Resolved target | configured channel + direct chat id, `source: explicit` |
| `fallbackUsed` | `true` — expected for an isolated job: delivery goes through the cron announce path, not through a source session |

The ping text opened with the day plan, then listed open items and one proposal — the shape that
`PRESENCE-PING.md` asks for.

## 2. The scheduler stays silent when the gate says no

The gate runs in code mode, before any model call. Between job creation and 15:40 MSK the
scheduler recorded **42 trigger evaluations and exactly one fire**:

| Observation | Value |
|---|---|
| `triggerEvalCount` | 41 → 42 across the 15:40 slot |
| `lastTriggerEvalAt` | 15:40:00 MSK |
| `lastTriggerFireAt` | 10:00:16 MSK (unchanged) |
| Agent runs in history | 3 (one fired slot + two manual debug runs) |
| New run at 15:40 | none |
| Message at 15:40 | none |

Two extra runs in the history are **manual** debug invocations, which bypass the trigger by design.
Both ended in `NO_REPLY`; delivery was suppressed with reason `silent` and `delivered: false` — the
"agent decided to stay quiet" path is separate from the gate and also verified.

## 3. Gate boundaries on the live host

`--now` overrides only the clock; silence, plan file, stream and holiday cache are the real ones.

| Moment (MSK) | Condition | Result |
|---|---|---|
| Sat 21:55 | last ping 09:55, silence 8 h 26 min | `fire: true` |
| Sat 22:00 | same state | `fire: false` — night window |
| Sun 09:30 | weekend, before 10:00 | `fire: false` |
| Mon 08:00 | weekday, after 07:00 | `fire: true` |
| Sat 21:55 | last ping 2 h ago | `fire: false` — spacing holds |
| Sat 13:30 | silence 1 min | `fire: false` |

## 4. Fresh announce probe

A one-shot job with the same `agentTurn` + `announce` shape was created for 15:33 MSK and deleted
itself after the run:

| Field | Value |
|---|---|
| `delivered` | `true` |
| `deliveryStatus` | `delivered` |
| Resolved target | same channel and direct chat id |
| Job after run | not found (auto-deleted) |

The stream hook recorded the matching outbound `message:sent` event for the same chat — the
write path and the delivery path agree.

## Still unverified

- **Matrix delivery.** The watcher is wired to one channel; a second channel would need its own
  job (one `delivery` target per job). Not exercised.
- **Failure alert.** `failureAlert.after: 2` is configured but was not triggered — no provider
  outage was staged.
- **Long-run drift.** 42 evaluations cover a few hours of one day, not weeks of scheduler restarts
  and DST-free timezone behaviour.

## Reproduce

```bash
# decision only, no model, no delivery
OPENCLAW_WORKSPACE=~/.openclaw/workspace \
  node scripts/living-loop/presence-check.mjs --now 2026-11-07T18:55:00Z

# what the scheduler thinks: evaluations, last fire, next slot
openclaw automations get <watcher-id> --json | jq '.state | {triggerEvalCount, lastTriggerEvalAtMs, lastTriggerFireAtMs}'
openclaw automations runs <watcher-id> --limit 5 --json | jq '.total'
```
